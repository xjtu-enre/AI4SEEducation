# ArchCompass 
## 架构指南针

ArchCompass 关注代码能够运行之后的结构质量问题。它通过实体依赖图识别模块之间的不合理关系，发现短期内不一定触发错误、但会持续增加理解成本和修改风险的架构反模式。

## 通用反模式

系统当前页面展示七类常见问题：

- **接口未解耦**：调用方同时依赖抽象与具体实现，削弱接口隔离效果。
- **循环依赖**：两个或多个模块形成依赖闭环，导致边界模糊。
- **循环继承**：继承关系形成环，破坏层次结构的单向性。
- **数据泥团**：一组数据在多个位置反复共同出现，说明缺少合适的封装。
- **特性依恋**：方法过度访问其他类的数据或能力，职责分配不合理。
- **多重路径继承**：子类通过多条路径到达同一父类，增加理解和维护难度。
- **霰弹式修改**：一次需求变化需要同时改动许多位置，说明职责过度分散。

## 检测方法

ArchCompass 将反模式定义为实体与依赖关系需要满足的结构条件，再把项目代码转换为依赖图，通过规则解析和子图匹配查找违规实例。页面既提供各类反模式的总体统计，也可以查看涉及的实体和关系。

## 自定义架构约束

不同课程可能对分层、继承、可见性和模块访问有不同要求。ArchCompass 提供自定义检查能力，将自然语言描述的架构约束转换为规则描述，再生成对应检查逻辑。既有项目材料记录了 6 类共 24 种架构违约检查，并在实验数据上验证了自然语言转换效果。

## 教学价值

架构原则往往停留在教材定义中，学生不容易把“低耦合、高内聚”映射到自己的代码。ArchCompass 把原则落实为具体实体、依赖路径和违规数量，使学生看到某个设计选择如何影响整个项目。教师也可以把课程设计约束转化为统一检查规则，减少不同作业之间的评价偏差。
