# Anti-Pattern Type
## 反模式类型
### 1）接口未解耦（Abstraction Without Decoupling）
接口未解耦指的是第三方类既依赖于父类，也依赖于子类，同时第三方类与所依赖的父类与子类之间不存在继承或实现接口的关系。对于 Java 语言，接口未解耦通常指的是一个类同时依赖于抽象类与其实现类。接口未解耦违反了依赖倒置原则（Dependency Inversion Principle）和接口可分离性原则（Interface Segregation Principle），导致组件间紧密耦合，降低了系统的可拓展性与可重用性。为避免接口未解耦，可通过依赖注入、代码审查等方式，重构解耦相关组件之间的依赖关系。
### 2）循环依赖（Cyclic Dependency）
循环依赖指的是软件系统中两个或多个组件、模块或类之间存在相互依赖，形成依赖闭环的关系。如模块 A 依赖于模块 B，模块 B 又依赖于模块 A，就形成了循环依赖。对于 Java 语言，循环依赖通常指的是类之间相互引用。循环依赖违反了无环依赖原则（Acyclic Dependency Principle），降低了代码的独立性，使得模块间的边界模糊，降低了系统的灵活性和可维护性。为避免循环依赖，可通过依赖注入、引入中间层等方式，将具体实现类的依赖关系抽象化，降低类之间的耦合度。
### 3）循环继承（Cyclic Hierarchy）
循环继承指的是父类直接或间接依赖于它的一个子类，即在类的继承关系中，形成了循环依赖的关系。如类 A 继承自类 B，类 B 又继承自类 C，而类 C 最终又继承自类 A，这样就形成了一个闭环。对于 Java 语言，循环继承通常指的是类之间存在环状的继承关系。循环继承违反了依赖倒置原则，破环了继承层次结构的清晰性和单向性，降低了代码的可理解性和可维护性。为避免循环继承，可通过引入接口等方式，减少类之间的耦合。
### 4）数据泥团（Data Clumps）
数据泥团指的是一组经常一起出现的数据项在多个地方重复出现。如在多个类中具有相同的字段，或在多个方法中具有相同的参数列表。数据泥团违反了单一职责原则（Single Responsibility Principle）和封装原则（Encapsulation principle），导致代码重复冗余，增加了代码的复杂性，降低了系统的可维护性。为避免数据泥团，可通过提炼类、引入参数对象等方式，将紧密关联的数据项组合成一个类或对象，提升代码的组织性。
### 5）特性依恋（Feature Envy）
特性依恋指的是一个模块过度依赖于另一个模块。对于 Java 语言，特性依恋通常指的是一个方法过度依赖于其他类中的方法而非其所属类中的方法。特性依恋违反了单一职责原则，使得类的责任分配不均衡，削弱了类的内聚性，增加了类之间的耦合度，降低了系统的可维护性。为避免特性依恋，可通过采用观察者模式、提炼或移动方法等方式，提升代码的内聚性，降低耦合度。
### 6）多重路径继承（Multipath Hierarchy）
多重路径继承指的是子类到其父类存在多条继承路径，发生在类与类之间。多重路径继承违反了单一职责原则，导致二义性问题，增加了类之间的耦合度，增加了系统的复杂性，降低了系统的可维护性。为避免多重路径继承，可通过使用接口或抽象类等方式，明确类之间的关系，提高系统的可维护性。
### 7）霰弹式修改（Shotgun Surgery）
霰弹式修改指的是当系统每遇到某种变化，都必须在许多不同的类内做出许多小修改。霰弹式修改违反了单一职责原则，致使类的职责分散，增加了类之间的耦合度，使得功能修改容易出错且难以追踪和测试，增加了系统的复杂性，降低了系统的可维护性。为避免霰弹式修改，可通过使用搬移函数和字段、内联函数或类等方式，减少修改时的风险，确保系统的稳定性和可靠性。
